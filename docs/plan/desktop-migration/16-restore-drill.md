# 16 — Backup/restore drill procedure

**Status:** draft · **Gates:** 5/6 candidate · **Date:** 2026-11-02 · **Related:** [`14-release-drill.md`](14-release-drill.md) (§3–4), [`13-implementation-status.md`](13-implementation-status.md)

This is the executable drill behind entry criterion E2 of
[`15-pilot.md`](15-pilot.md). Run it green on the release build before any
pilot starts. It makes no claim about signing: until signing lands, run the
drill on unsigned smoke builds for procedure only and re-run on the signed
build before the pilot.

> **Status note.** An earlier draft of this drill noted that no `restore`
> subcommand existed. It now does: `hragents-cli restore <backup> <db>
> [--force]` implements exactly the §3 contract below (verify-first,
> refuse-overwrite-newer without `--force`, snapshot live, temp+atomic swap,
> re-verify), and the drill in §4 runs it for real.

## 1. Prerequisites

| Item | Detail |
|---|---|
| PROD machine (or VM snapshot) | Clean OS per `14-release-drill.md` §2; record OS build + WebView2/WebKit version |
| SPARE machine (or second VM snapshot) | Restore target; must not share a filesystem lock with PROD |
| Build under test | Release build under test; record version + installer SHA-256 |
| Test DB | Generated by the demo harness (deterministic seed data) |
| Removable media or network share | To carry the backup file from PROD to SPARE (simulates off-machine recovery) |
| Operator | Named person running the drill; second person witnessing sign-off |

## 2. Commands (CLI demo harness)

Run from `rust/`:

```bash
cargo run -p hragents-cli -- demo <db>
cargo run -p hragents-cli -- verify <db>
cargo run -p hragents-cli -- backup <db> <out>
```

What each does (per `hragents-cli/src/main.rs` + `hragents-store`):

- `demo <db>` — deletes `<db>` if present, seeds a demo company (login,
  employee, onboarding, evaluation + gated rejection, leave, payroll, audit),
  prints the audit head hash, writes `<db-dir>/hragents-demo-backup.db` via
  `rusqlite::backup`, prints a search hit count. Ends with `demo complete`.
- `verify <db>` — opens the store read path, runs audit-chain verification
  (`ok: N audit entries, head <hash>`) and `PRAGMA integrity_check`
  (`integrity: ok`). Nonzero exit on any failure.
- `backup <db> <out>` — opens the store, copies via `rusqlite::backup`,
  prints `backup: <bytes> at <out>`.

## 3. Restore contract (required; enforced manually until a subcommand exists)

Any restore path — manual steps or a future `restore` subcommand — MUST:

1. **Verify the backup first.** Run audit verification + `integrity_check`
   against the backup file before touching the live DB. A backup that fails
   either check is rejected; the drill stops.
2. **Never merge.** Restore replaces the live DB file; it never merges rows.
3. **Refuse to overwrite a newer live DB without an explicit flag.** Compare
   live vs backup (audit head / `updated_at` / file mtime recorded in the
   drill log). If the live DB is newer, abort unless the operator passes an
   explicit `--force-overwrite-newer` style confirmation (typed, not a bare
   retry). Record which path was taken.
4. **Snapshot the current live DB first.** Copy the live DB aside before
   overwriting, so a bad restore is recoverable.
5. **Restore to temp, then atomic swap.** Copy the backup to a temp file
   beside the target, verify the temp copy, then atomically rename over the
   target. No partial live DB may exist.
6. **Re-verify after copy.** Run `verify` on the restored DB (audit entries,
   head hash, `integrity: ok`) and confirm accounts + audit history survived
   before restart is declared a success.

## 4. Drill steps with expected outputs

On PROD:

| Step | Command / action | Expected output |
|---|---|---|
| P1 | `cargo run -p hragents-cli -- demo /tmp/drill/prod.db` | `demo complete`; audit line shows 16 entries; backup file written |
| P2 | `cargo run -p hragents-cli -- verify /tmp/drill/prod.db` | `ok: 16 audit entries, head <12-hex>`; `integrity: ok`; exit 0 |
| P3 | `cargo run -p hragents-cli -- backup /tmp/drill/prod.db /tmp/drill/prod.hrbackup` | `backup: <bytes> at /tmp/drill/prod.hrbackup` |
| P4 | `cargo run -p hragents-cli -- verify /tmp/drill/prod.hrbackup` | `integrity: ok`; exit 0 (backup verified at creation) |
| P5 | Record audit head hash + file SHA-256 of both files in the drill log | Hashes recorded |

Carry `/tmp/drill/prod.hrbackup` to SPARE (removable media/share). On SPARE:

| Step | Command / action | Expected output |
|---|---|---|
| S1 | `cargo run -p hragents-cli -- verify /tmp/drill/prod.hrbackup` | `integrity: ok` — backup verified **before** touching anything |
| S2 | Snapshot: `cp spare-live.db spare-live.db.pre-restore.<ts>` (or note "no live DB") | Snapshot path recorded |
| S3 | Newer-check: compare live DB recency vs backup; if live is newer and no force flag, **stop** | Refusal recorded, or explicit force confirmation recorded |
| S4 | Copy backup to temp, verify temp, atomic rename over target | `verify <target>` → same audit head hash as P5; `integrity: ok` |
| S5 | `cargo run -p hragents-cli -- demo` is NOT re-run; instead open the app (or store) on the restored DB and confirm the employee, evaluation, leave, payroll, and audit entries match P5 | Accounts + audit history survive; audit verifies after restart |

S5 passes only if the restored DB is byte-for-byte accountable to P5 hashes
and the audit head matches.

## 5. Failure injection (must fail closed)

| Step | Action | Expected |
|---|---|---|
| F1 | Copy the verified backup to `/tmp/drill/corrupt.db`; flip bytes in the middle (`printf '\xFF' \| dd of=corrupt.db bs=1 seek=4096 conv=notrunc`) | Corrupt copy differs in SHA-256 from the backup |
| F2 | `cargo run -p hragents-cli -- verify /tmp/drill/corrupt.db` | Nonzero exit and/or `integrity` failure; audit verification fails. **Fail closed:** no partial "ok". |
| F3 | Attempt the §3 restore path with the corrupt file | Rejected at contract step 1 (verify-first). Live DB untouched: re-run `verify` on the live DB → still `ok`, head hash unchanged from the drill log. |
| F4 | Record the live-DB head hash before and after F2–F3 | Identical. Any difference is a drill failure and a stop-work event. |

## 6. Rollback rehearsal (reinstall previous version + restore)

Follows `14-release-drill.md` §4; Tauri cannot downgrade in place:

1. Install signed build N−1 on SPARE, create data, back up (`backup` +
   `verify`, hashes logged).
2. Install signed build N; migration runs (backup first → migrate in one
   transaction → `quick_check` → audit verify).
3. Simulate a failed migration; confirm automatic restore of the pre-update
   backup and relaunch of the cached previous installer from `updates/cache/`
   (kept 7 days).
4. Manual rollback: reinstall cached N−1, restore the pre-update backup per
   the §3 contract, re-verify audit.
5. Confirm a newer-schema DB refuses to open on the older binary (no silent
   downgrade); record the exact error.

On unsigned smoke builds, rehearse steps 1–4 for procedure and re-run on the
signed build before claiming E2.
